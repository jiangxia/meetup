## ⚡ 技术风险控制

### 最高优先级风险: 原生MCP Client集成
**风险**: 原生MCP协议实现可能复杂，stdio/HTTP通信调试困难
**控制方案**:
- Day 1 上午前2小时立即验证MCP连接
- 准备stdio和HTTP两种传输方式
- 如果MCP调用失败，准备Mock PromptX响应降级
- 提前测试JSON-RPC 2.0消息格式

### 次优先级风险: 原生OpenAI API调用
**风险**: 无框架保护的API调用，错误处理复杂
**控制方案**:
- 实现robust的fetch错误处理和重试机制
- 准备多个API密钥轮换
- 流式响应的SSE连接异常处理
- 准备固定回复降级方案

### 界面开发风险: 时间不够美化
**风险**: 界面粗糙影响演示效果
**控制方案**:
- 使用现成的CSS框架(Bootstrap/Tailwind)
- 准备简单但有效的酒馆风格模板
- 优先功能实现，最后美化界面

## 🛠️ 技术栈决策 (最终确定)

### 前端技术 (确定)
```javascript

  样式: "CSS Grid + Flexbox + 酒馆主题 (无框架依赖)",

  存储: "LocalStorage (会话级) + PromptX记忆系统",
  部署: "本地开发 (黑客松演示版)"
}
```

### 后端架构 (纯原生确定)
- **选定方案**: Node.js + Express + 原生实现
- **核心组件**: 原生MCP Client + 原生OpenAI API调用
- **作用**: 处理CORS、保护API密钥、标准MCP协议通信
- **优势**: 零框架依赖，完全可控，启动快速，调试简单

### LLM API (原生调用确定)
- **确定选择**: 原生fetch调用OpenAI GPT-4o-mini API
- **实现方式**: 原生HTTP请求 + 流式SSE响应
- **原因**: 无框架抽象，直接控制，便宜快速
- **备选**: 固定Mock回复 (降级方案)

### PromptX集成 (原生MCP确定)
- **协议**: 标准MCP (Model Context Protocol) JSON-RPC 2.0
- **传输**: stdio进程通信 (主要) + HTTP (备选)
- **工具**: promptx_remember, promptx_recall, promptx_action
- **集成方式**: 原生MCP Client直接调用PromptX MCP Server
- **优势**: 标准协议，无自定义桥接，直接使用PromptX所有功能
